# Техническое задание

## Система поиска, ранжирования, расширения контекста и генерации ответа поверх RAG-корпуса психологической литературы

## 1. Общие сведения

### 1.1. Наименование системы

Система retrieval и answer synthesis для психологического RAG-корпуса на базе self-hosted Qdrant и LLM.

### 1.2. Назначение

Система предназначена для поиска релевантных фрагментов в корпусе психологической литературы по пользовательскому описанию состояния, их многоэтапного ранжирования, расширения найденного контекста и формирования итогового ответа для пользователя.

### 1.3. Цель

Обеспечить такой поисковый pipeline, при котором пользователь получает:

* релевантные советы по своему состоянию;
* практические техники и упражнения;
* объяснение состояния в понятной форме;
* рекомендации, основанные на найденных источниках;
* ответ, ограниченный техническими рамками канала доставки, включая лимит Telegram.

---

## 2. Область применения

Система должна использоваться в составе ИИ-ассистента психологической поддержки и обслуживать сценарии:

* быстрый совет по описанию состояния;
* подбор техник и упражнений;
* поиск объясняющих теоретических фрагментов;
* поиск упражнений, рабочих листов и чек-листов;
* поддержка сценариев бота «Кора», где требуется доступ к знаниям из корпуса.

---

## 3. Основной сценарий работы

Система должна поддерживать следующий базовый сценарий:

1. Пользователь описывает своё состояние, проблему, запрос или ситуацию.
2. Входной запрос передаётся в LLM-модуль интерпретации запроса.
3. LLM формирует структурированный JSON с набором поисковых запросов и параметров поиска.
4. По каждому запросу выполняется поиск в Qdrant.
5. Полученные результаты объединяются, очищаются от дублей и проходят ranking/re-ranking.
6. На основе первичного поискового массива система определяет наиболее полезные запросы и/или наиболее полезные найденные кластеры результатов.
7. Для лучших результатов выполняется расширение контекста: извлекаются более крупные фрагменты, например раздел, подглава или глава.
8. Исходный пользовательский запрос, найденные фрагменты и метаданные передаются в LLM-модуль генерации ответа.
9. LLM формирует итоговый ответ для пользователя в виде списка советов, шагов, объяснений и опционально ссылок на источник в терминах книги/главы/страниц.
10. Ответ адаптируется под ограничения канала доставки, включая ограничение Telegram в 4096 символов на одно сообщение.
11. Пользователь получает один или несколько сообщений с финальным ответом.

---

## 4. Основные требования к системе

### 4.1. Входной запрос

Система должна принимать на вход:

* текстовое сообщение пользователя;
* идентификатор пользователя;
* идентификатор сценария;
* язык запроса;
* технические параметры вызова;
* при наличии — пользовательский контекст из профиля или интервью.

### 4.2. Нормализация запроса

Перед генерацией поисковых запросов система должна уметь:

* очистить служебный шум;
* выделить симптомы, эмоции, ситуации и цели запроса;
* определить, нужен ли быстрый совет, теория, техника, упражнение или смешанный ответ;
* выявить признаки срочности;
* выявить тематические теги, подходящие для фильтрации поиска.

### 4.3. Генерация поисковых запросов

Система должна генерировать не один поисковый запрос, а набор альтернативных запросов для retrieval.

### 4.4. Многоэтапный retrieval

Система должна выполнять:

* первичный поиск по чанкам;
* объединение результатов;
* ranking и re-ranking;
* отбор наиболее полезных результатов;
* расширение контекста до более крупных единиц.

### 4.5. Генерация итогового ответа

Система должна формировать ответ только на основе:

* исходного запроса пользователя;
* найденных и расширенных фрагментов;
* метаданных этих фрагментов;
* заданных правил ответа и ограничений сценария.

### 4.6. Ограничение Telegram

Система должна обеспечивать безопасную отправку ответа в Telegram с учётом ограничения 4096 символов на одно сообщение.

### 4.7. Конфигурируемость

Все количественные и логические параметры pipeline должны быть настраиваемыми без изменения архитектуры системы.

---

## 5. Архитектурные компоненты

Система должна включать следующие логические компоненты:

1. **Input Interpreter** — анализ пользовательского сообщения.
2. **Query Planner** — генерация набора поисковых запросов в JSON.
3. **Retriever** — выполнение поиска в Qdrant.
4. **Candidate Merger** — объединение и дедупликация результатов.
5. **Ranker / Re-ranker** — повторное ранжирование результатов.
6. **Useful Query Selector** — выбор наиболее ценных поисковых направлений.
7. **Context Expander** — получение расширенных контекстов по лучшим находкам.
8. **Answer Composer** — генерация итогового ответа через LLM.
9. **Telegram Formatter** — упаковка ответа в одно или несколько сообщений.
10. **Logging & Audit Layer** — журналирование этапов поиска и генерации.

---

## 6. Логика обработки запроса

## 6.1. Этапы pipeline

Pipeline должен включать следующие этапы:

1. Получение пользовательского запроса
2. Регистрация поисковой сессии
3. Нормализация и интерпретация запроса
4. Генерация JSON-набора поисковых запросов
5. Первичный retrieval по Qdrant
6. Объединение кандидатов
7. Ranking / re-ranking
8. Отбор наиболее полезных запросов и результатов
9. Расширение контекста до разделов/глав
10. Генерация финального ответа
11. Адаптация ответа под Telegram
12. Сохранение артефактов и статуса выполнения

---

## 7. Требования к интерпретации пользовательского запроса

Система должна уметь автоматически выделять из сообщения пользователя:

* описание состояния;
* основные эмоции;
* симптомы и трудности;
* контекст ситуации;
* предполагаемую тему;
* желаемый тип ответа;
* уровень срочности;
* признаки кризисного состояния;
* предпочтительную глубину ответа.

### 7.1. Целевые типы ответа

Система должна уметь определять, что пользователю нужен один или несколько типов ответа:

* быстрый совет;
* объяснение состояния;
* подбор техники;
* упражнение;
* психообразование;
* поддерживающий ответ;
* список практических шагов;
* кризисная информация.

### 7.2. Тематическое распознавание

Система должна уметь сопоставлять запрос с тематическими тегами корпуса, например:

* тревога;
* депрессия;
* паника;
* ОКР;
* стресс;
* травма;
* бессонница;
* самокритика;
* избегание;
* отношения;
* выгорание.

---

## 8. Требования к генерации поисковых запросов LLM

## 8.1. Общие требования

LLM должна формировать **структурированный JSON строго по заданной схеме**, пригодный для автоматического исполнения без дополнительного ручного преобразования.

### 8.2. Количество запросов

Система должна уметь генерировать набор поисковых запросов, количество которых задаётся конфигурацией.

По умолчанию система должна поддерживать генерацию до:

* `50` поисковых запросов на один пользовательский запрос.

Это значение должно быть настраиваемым.

### 8.3. Типы поисковых запросов

Набор запросов должен включать разные типы поисковых формулировок, например:

* симптом-ориентированные;
* проблемно-ситуационные;
* теоретические;
* практические;
* запросы на упражнения;
* запросы на рабочие листы;
* запросы на кейсы;
* запросы на кризисную информацию;
* узкие запросы по технике;
* расширенные обобщающие запросы.

### 8.4. Требования к разнообразию

Система должна стремиться к тому, чтобы сгенерированные запросы не дублировали друг друга, а покрывали разные ракурсы пользовательского запроса.

### 8.5. Обязательная JSON-схема поискового плана

Минимально JSON должен поддерживать следующий формат:

```json
{
  "schema_version": "1.0",
  "request_id": "uuid",
  "user_query": "Мне тревожно, я плохо сплю и постоянно прокручиваю в голове плохие сценарии",
  "language": "ru",
  "search_profile": "quick_advice",
  "normalized_state": {
    "summary": "Тревога с руминацией и нарушением сна",
    "symptoms": ["тревога", "руминация", "бессонница"],
    "situations": ["вечер", "перед сном"],
    "goal": "получить быстрый совет и техники",
    "urgency": "normal"
  },
  "global_filters": {
    "language": ["ru"],
    "source_type": ["самопомощь", "практическое пособие", "академический"],
    "exclude_content_types": [],
    "prefer_content_types": ["exercise", "worksheet", "text", "checklist"]
  },
  "queries": [
    {
      "query_id": "q1",
      "text": "тревога перед сном техники самопомощи",
      "intent_type": "technique",
      "weight": 1.0,
      "topic_tags": ["тревога", "бессонница"],
      "approach_tags": ["КПТ", "самопомощь"],
      "preferred_content_types": ["exercise", "checklist", "text"],
      "expected_granularity": "chunk"
    }
  ]
}
```

### 8.6. Поля поискового запроса

Для каждого отдельного запроса должны поддерживаться как минимум поля:

* `query_id`
* `text`
* `intent_type`
* `weight`
* `topic_tags`
* `approach_tags`
* `preferred_content_types`
* `expected_granularity`

### 8.7. Расширяемость схемы

В будущем схема должна позволять добавлять:

* отрицательные условия;
* строгие фильтры по автору или книге;
* приоритет по типу источника;
* приоритет по глубине материала;
* сигналы для гибридного поиска;
* отдельные поисковые стратегии для сценариев «Отношения», «Привычки», «Техники».

---

## 9. Требования к поиску в Qdrant

## 9.1. Назначение

Qdrant используется как хранилище первичных поисковых единиц — чанков документа с текстом, векторами и метаданными.

### 9.2. Поисковая единица

Первичный поиск должен выполняться по чанкам.

### 9.3. Используемые данные

При поиске система должна использовать:

* dense vector поиска;
* payload-метаданные;
* текст чанка;
* заголовочную иерархию;
* тип контента;
* тематические теги;
* признаки OCR;
* структурные привязки к разделам.

### 9.4. Требования к фильтрации

Система должна поддерживать фильтрацию по метаданным, включая:

* `document_id`
* название книги
* автор
* язык
* `content_type`
* `source_type`
* `topic_tags`
* `approach_tags`
* `chapter_no`
* `chapter_title`
* `subchapter_no`
* `subchapter_title`
* `ocr_used`
* страницы

### 9.5. Поиск по нескольким запросам

Для одного пользовательского обращения система должна уметь выполнять поиск по множеству запросов и собирать единый пул кандидатов.

### 9.6. Настраиваемые параметры retrieval

Должны настраиваться как минимум:

* число поисковых запросов;
* `top_k` на один запрос;
* общий лимит кандидатов;
* минимальный score;
* фильтры по контент-типам;
* режим поиска;
* лимит по одной книге;
* лимит по одной главе.

---

## 10. Требования к ranking и re-ranking

## 10.1. Первичное ранжирование

Первичный поиск должен формировать список кандидатов на основе векторной близости и фильтрации по payload.

### 10.2. Объединение результатов

После поиска по всем запросам система должна:

* объединить кандидатов;
* удалить точные дубли;
* по возможности удалить почти одинаковые чанки;
* сохранить трассировку, какой запрос привёл к какому результату.

### 10.3. Повторное ранжирование

Система должна поддерживать re-ranking с учётом:

* исходного пользовательского запроса;
* текста найденного чанка;
* `content_type`;
* `heading_path`;
* тематических тегов;
* структурной близости к запросу;
* полезности для текущего сценария.

### 10.4. Приоритеты ранжирования

Re-ranking должен уметь повышать релевантность:

* упражнений и техник, если пользователь просит практический совет;
* теоретических фрагментов, если пользователь просит объяснение;
* чек-листов и рабочих листов, если нужен структурированный инструмент;
* кризисной информации, если присутствуют признаки риска;
* высококачественных структурированных чанков над неструктурированными;
* не-OCR или качественных OCR-результатов над низкокачественным OCR, если есть равнозначные альтернативы.

### 10.5. Диверсификация

Система должна предотвращать ситуацию, когда весь топ результатов берётся:

* только из одной книги;
* только из одной главы;
* только одного типа контента;
* только из однотипных формулировок.

### 10.6. Выход re-ranking этапа

Результатом этапа должен быть отсортированный список кандидатов с метаданными и score’ами.

---

## 11. Требования к отбору наиболее полезных запросов

## 11.1. Назначение

После первичного поиска и re-ranking система должна уметь определить, какие из сгенерированных запросов оказались наиболее полезными с точки зрения качества найденного материала.

### 11.2. Количество полезных запросов

Система должна по умолчанию выбирать:

* `10` наиболее полезных запросов.

Количество должно быть настраиваемым.

### 11.3. Критерии полезности запроса

Полезность запроса должна определяться по совокупности факторов:

* число релевантных результатов;
* средний score результатов;
* покрытие разных аспектов пользовательского запроса;
* наличие практических материалов;
* наличие структурно богатых источников;
* отсутствие дублирования с другими запросами.

### 11.4. Выход этапа

Результатом должен быть список отобранных запросов, например:

```json
{
  "selected_queries": [
    {
      "query_id": "q7",
      "reason": "даёт лучшие практические техники для вечерней тревоги",
      "coverage": ["тревога", "сон", "самопомощь"],
      "score": 0.91
    }
  ]
}
```

---

## 12. Требования к расширению контекста

## 12.1. Назначение

После выбора лучших результатов система должна извлекать не только отдельные чанки, но и более крупные структурные единицы документа.

### 12.2. Режимы расширения

Система должна поддерживать режимы расширения:

* соседние чанки;
* смысловой блок;
* раздел;
* подглава;
* глава.

### 12.3. Правила расширения

При расширении контекста система должна использовать:

* `heading_path`;
* `chapter_no`, `chapter_title`;
* `subchapter_no`, `subchapter_title`;
* идентификаторы блоков;
* соседние чанки по порядку;
* диапазоны страниц.

### 12.4. Приоритетный режим

По умолчанию должен использоваться режим:

* `section` или `subchapter`.

Переход к целой главе должен выполняться, если:

* найденный чанк является частью цельного большого объяснения;
* пользователь просит более глубокий ответ;
* лимит контекста LLM это допускает;
* вся глава важна для корректной интерпретации.

### 12.5. Ограничения расширения

Расширение контекста не должно:

* переполнять доступный контекст LLM;
* добавлять нерелевантные разделы;
* смешивать разные темы без необходимости;
* разрушать связь с источником и страницами.

### 12.6. Выход этапа

Система должна формировать набор расширенных контекстов, например:

```json
{
  "expanded_contexts": [
    {
      "seed_chunk_id": "chunk_123",
      "expansion_mode": "section",
      "document_id": "doc_1",
      "chapter_title": "Работа с тревожными мыслями",
      "page_start": 114,
      "page_end": 119,
      "text": "..."
    }
  ]
}
```

---

## 13. Требования к генерации итогового ответа

## 13.1. Общие требования

LLM должна формировать итоговый ответ на основе:

* исходного запроса пользователя;
* лучших найденных результатов;
* расширенного контекста;
* метаданных источников;
* логики сценария.

### 13.2. Формат итогового ответа

Итоговый ответ должен содержать:

* краткое отражение запроса пользователя;
* 3–7 наиболее полезных рекомендаций или шагов;
* при необходимости — одну быструю технику;
* при необходимости — одну более глубокую практику;
* краткое объяснение, почему это может помочь;
* опционально — указание на источник в виде книги/главы/страниц;
* при необходимости — мягкое указание на ограничения ответа.

Количество советов должно быть настраиваемым.

### 13.3. Требования к grounded generation

Итоговый ответ не должен:

* выдумывать источники;
* ссылаться на неиспользованные материалы;
* делать категоричные выводы, не подтверждённые retrieved-контекстом;
* подменять найденные материалы непроверенными утверждениями модели.

### 13.4. Приоритет ответа

Система должна отдавать приоритет:

* практической полезности;
* релевантности текущему состоянию пользователя;
* бережной формулировке;
* структурированности;
* краткости, если канал доставки ограничен.

### 13.5. Требования к стилю ответа

Ответ должен быть:

* понятным;
* не перегруженным;
* нейтральным;
* бережным;
* не осуждающим;
* без избыточной академической громоздкости, если пользователь просит быстрый совет.

---

## 14. Требования к ограничениям Telegram

## 14.1. Общие требования

Система должна учитывать ограничение Telegram:

* не более `4096` символов на одно сообщение.

### 14.2. Безопасный внутренний лимит

Система должна использовать настраиваемый внутренний безопасный лимит, по умолчанию меньше максимума Telegram, например:

* `3800`–`3900` символов на сообщение,

чтобы учитывать служебные символы, форматирование и возможные расхождения в подсчёте.

### 14.3. Правила упаковки ответа

Если ответ превышает лимит, система должна:

* разбивать его на несколько сообщений;
* по возможности делить по смысловым абзацам;
* не разрывать пункт списка посередине;
* маркировать части как `1/2`, `2/2` и т. п.;
* сохранять читабельность каждой части.

### 14.4. Предпочтительная стратегия

Система должна стремиться:

1. сначала уместить ответ в одно сообщение;
2. если это невозможно — разбить ответ на несколько логических частей;
3. при необходимости вынести подробные источники в отдельное сообщение.

### 14.5. Требования к длине

Система должна уметь отдельно настраивать:

* максимальную длину одного сообщения;
* максимальное число сообщений на ответ;
* объём основного ответа;
* объём блока с источниками;
* объём блока с дополнительными советами.

---

## 15. Требования к конфигурируемости

Все константы и пороги должны быть вынесены в конфигурацию.

### 15.1. Обязательные настраиваемые параметры

Минимально должны настраиваться:

* число поисковых запросов;
* число результатов на запрос;
* общий лимит кандидатов;
* минимальный score отбора;
* число запросов, проходящих в финальный shortlist;
* число расширяемых seed-результатов;
* режим расширения контекста;
* лимит символов расширенного контекста;
* лимит токенов для LLM;
* число рекомендаций в ответе;
* лимит символов Telegram-сообщения;
* число частей Telegram-ответа;
* веса ranking и re-ranking;
* фильтры по типам контента;
* фильтры по source_type;
* версии промптов;
* версии JSON-схем;
* режимы обработки кризисных кейсов.

### 15.2. Требования к профилям

Система должна поддерживать поисковые профили, например:

* `quick_advice`
* `psychoeducation`
* `exercise_search`
* `worksheet_search`
* `relationship_support`
* `habit_support`
* `crisis_sensitive`

Каждый профиль должен иметь собственные настройки весов и лимитов.

## 16. Требования к расширяемости

Система должна позволять в будущем:

* подключать sparse vectors;
* использовать гибридный поиск;
* использовать отдельный reranker;
* подключать несколько embedding-моделей;
* подключать несколько LLM для разных этапов;
* использовать отдельные retrieval-профили по сценариям;
* добавлять дополнительные поля фильтрации;
* добавлять новый канал доставки помимо Telegram;
* использовать knowledge graph или rule-based post-filtering.

## 19. Требования к качеству поиска

## 19.1. Полнота

Система должна обеспечивать покрытие основных аспектов пользовательского запроса за счёт множества поисковых формулировок.

## 19.2. Релевантность

Итоговый top результатов должен соответствовать не просто ключевым словам, а смыслу пользовательского состояния.

## 19.3. Практическая полезность

Для сценария быстрого совета система должна уметь находить не только теорию, но и применимые техники.

## 19.4. Структурная корректность

При расширении контекста не должна теряться связь с:

* книгой;
* главой;
* подглавой;
* страницами;
* типом контента.

## 19.5. Воспроизводимость

При фиксированных версиях моделей и одинаковых настройках результат должен быть максимально стабилен.

## 20. Требования к кризисным и чувствительным запросам

### 20.1. Общие требования

Система должна уметь выделять запросы, требующие осторожной обработки.

### 20.2. Признаки чувствительности

Должны распознаваться сигналы:

* кризиса;
* суицидального риска;
* острой дезорганизации;
* экстренной необходимости помощи.

### 20.3. Приоритет поиска

Для таких запросов система должна повышать приоритет:

* кризисной информации;
* безопасных стабилизирующих рекомендаций;
* материалов с тегами специальной обработки.

### 20.4. Ограничения генерации

В чувствительных сценариях ответ не должен быть исключительно теоретическим. Система должна уметь формировать более осторожный и безопасный формат ответа.

## 24. Нефункциональные требования

### 24.1. Масштабируемость

Система должна поддерживать рост корпуса и числа запросов без изменения базовой архитектуры.

### 24.2. Расширяемость

Система должна позволять заменять:

* embedding-модель;
* модель query planner;
* модель reranker;
* модель финальной генерации;
* транспортный канал.

### 24.3. Наблюдаемость

Система должна позволять понять:

* какой поисковый запрос сработал лучше всего;
* какие чанки были отброшены и почему;
* почему был выбран тот или иной расширенный контекст;
* почему ответ был разбит на несколько сообщений.

### 24.4. Воспроизводимость

При фиксированной версии pipeline все этапы должны быть воспроизводимы.

### 24.5. Отказоустойчивость

При сбое отдельного этапа система должна:

* корректно зафиксировать ошибку;
* сохранить промежуточные артефакты;
* вернуть управляемый статус;
* по возможности деградировать в более простой режим, а не полностью падать.

---

## 25. Ограничения и допущения

### 25.1. Ограничения

* Не все пользовательские состояния могут быть выражены точными поисковыми терминами.
* Не все полезные материалы найдутся в одном проходе retrieval.
* Расширение до главы может быть слишком объёмным для контекста LLM.
* OCR-качество корпуса может влиять на полноту поиска.
* Telegram ограничивает объём итогового ответа.

### 25.2. Допущения

* Корпус уже проиндексирован в Qdrant.
* У чанков есть валидные метаданные структуры.
* Для retrieval доступна хотя бы одна embedding-модель.
* Для re-ranking и финальной генерации доступна хотя бы одна LLM.
* В корпусе есть достаточное количество русскоязычных материалов для сценариев поддержки.

---

## 26. Критерии приёмки

Система считается принятой, если выполняются следующие условия:

1. Пользовательский запрос корректно проходит весь retrieval pipeline.
2. LLM формирует валидный JSON поискового плана по утверждённой схеме.
3. По набору поисковых запросов выполняется поиск в Qdrant.
4. Результаты объединяются, ранжируются и повторно ранжируются.
5. Система выбирает shortlist наиболее полезных запросов и/или результатов.
6. Для лучших результатов извлекаются более крупные контексты.
7. Итоговый ответ формируется на основе найденного корпуса, а не произвольной генерации.
8. Ответ может быть доставлен в Telegram без нарушения ограничения 4096 символов на сообщение.
9. Для каждой поисковой сессии сохраняются артефакты и журнал обработки.
10. Все количественные параметры pipeline настраиваются через конфигурацию.
11. Архитектура допускает расширение retrieval и ranking-логики без полной переработки системы.

## 28. Результат работы системы

Результатом обработки одного пользовательского запроса должны быть:

1. Нормализованное представление запроса.
2. JSON-план поисковых запросов.
3. Набор retrieved-результатов из Qdrant.
4. Ранжированный shortlist результатов.
5. Расширенные контексты по лучшим находкам.
6. Финальный ответ для пользователя.
7. Набор Telegram-safe сообщений.
8. Полный журнал поисковой сессии.
9. Статус успешной или неуспешной обработки.

---

Ниже — короткая формулировка архитектуры в одну строку, которую можно дать разработчику как суть:

**User query → LLM Query Planner → multi-query retrieval in Qdrant → merge → ranking/re-ranking → select best search intents/results → expand context to section/chapter → LLM grounded answer synthesis → Telegram-safe response packaging.**

Могу следующим сообщением сразу сделать ещё и **API-спецификацию этого поиска**: `POST /search`, JSON request/response, статусы, DTO и пример payload для бэкенда.
